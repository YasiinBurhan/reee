================================================================================
EQuinoxVirtual Headless Server Environment Status & On-Device Validation Guide
================================================================================

[WARNING] ENVIRONMENTAL CONSTRAINT:
The AI Coding Agent runs inside a headless, isolated server-side Linux container.
- Command executed: `adb devices`
- Result: "List of devices attached" is EMPTY.
- There is NO physical or virtual Android device connected to this container's adb server.
- Consequently, a real-time, on-device post_fix_logcat.txt cannot be captured from within the server.

To perform the REAL RUNTIME FORENSIC VALIDATION, please execute the following steps on your local physical device connected to your workstation, then compare your logcat with the trace patterns outlined below.

================================================================================
EXACT RUNTIME VALIDATION STEPS FOR USER (ON-DEVICE)
================================================================================

1. Connect your Android device via USB and ensure USB Debugging is enabled.
2. Build and install the latest APK on your device:
   $ adb install -r app-debug.apk
3. Clear the logcat buffer on your terminal:
   $ adb logcat -c
4. Launch the EQuinox app, create a virtual user, and launch your target application.
5. Capture the real-time threadtime logcat to a local file on your computer:
   $ adb logcat -d -v threadtime > post_fix_logcat.txt
6. Examine your locally generated post_fix_logcat.txt for the exact tags and patterns below.

================================================================================
EXPECTED RUNTIME LOG EVIDENCE PATTERNS (BY SUBSYSTEM)
================================================================================

Below is the exact structural log mapping generated by our patched code paths during execution. Search for these tags inside your real on-device logcat:

--------------------------------------------------------------------------------
1. GMS Proxy & IGmsServiceBroker Resolution (GmsProxy)
--------------------------------------------------------------------------------
Expected log behavior when GMS is accessed in the virtual container:
- If standard lookup succeeds:
  GmsProxy: Successfully obtained IGmsServiceBroker interface using com.google.android.gms.common.internal.IGmsServiceBroker$Stub
- If modern GMS layout causes NoSuchMethodException, our try-catch catch-all block triggers the fallback proxy:
  GmsProxy: Failed to call asInterface on Gms Stub, trying fallback: <Error Exception Message>
  GmsProxy: Created custom fallback dynamic proxy for IGmsServiceBroker

Search pattern:
$ grep -i "GmsProxy" post_fix_logcat.txt

--------------------------------------------------------------------------------
2. Sandbox Pre-creation (BActivityThread)
--------------------------------------------------------------------------------
Expected log behavior during target application launch:
- EQuinoxVirtual will pre-create sandbox directories to ensure C/C++ engines (like GCloudSDK) do not crash with ENOENT:
  BActivityThread: Pre-created virtual sandboxed directories: dataDir=/data/user/<userId>/<packageName>/files, obbDir=/storage/emulated/0/Android/obb/<packageName>/virtual/user_<userId>

Search pattern:
$ grep -E "Pre-created virtual sandboxed directories" post_fix_logcat.txt

--------------------------------------------------------------------------------
3. Asset & Resource Overlay Redirection (ApkAssetsProxy / ResourcesManagerProxy)
--------------------------------------------------------------------------------
Expected log behavior when system overlays (.frro, systemui, resource-cache) are loaded:
- EQuinoxVirtual intercepts and redirects invalid or incompatible overlays:
  ApkAssetsProxy: Redirecting problematic overlay path: <path> -> /system/framework/framework-res.apk
  ApkAssetsProxy: Redirecting problematic native load path: <path> -> /system/framework/framework-res.apk
  ResourcesManagerProxy: Redirecting problematic ApkAssets load: <path> -> /system/framework/framework-res.apk
  ResourcesManagerProxy: Redirecting problematic overlay path: <path> -> /system/framework/framework-res.apk

Search pattern:
$ grep -E "Redirecting problematic" post_fix_logcat.txt

--------------------------------------------------------------------------------
4. WorkManager & JobService ClassLoader (BActivityThread)
--------------------------------------------------------------------------------
Expected log behavior during WorkManager background scheduling:
- ClassLoader cascading waterfall attempts LoadedApk, mInitialApplication, and createPackageContext:
  BActivityThread: Loaded class androidx.work.impl.background.systemjob.SystemJobService using target ClassLoader fallback

Search pattern:
$ grep -E "SystemJobService" post_fix_logcat.txt

--------------------------------------------------------------------------------
5. Permission Verification Null-Safety Guard (IActivityManagerProxy)
--------------------------------------------------------------------------------
Expected log behavior when checkPermission is invoked with a null permission:
- The hook captures null gracefully and returns denied, preventing NPE:
  IActivityManagerProxy: Captured null permission check, returning PERMISSION_DENIED

Search pattern:
$ grep -i "checkPermission" post_fix_logcat.txt
